1. VISÃO GERAL DO PROJETO
-------------------------------------------------------------------------------
O Regz é uma plataforma completa para Gestão de Pessoas, acompanhamento de colaboradores, mapeamento geográfico por GPS/CEP, controle de permissões de acesso (RBAC) e criação de campos dinâmicos customizados.

Stack Tecnológica:
- Frontend: React 18, Vite, TypeScript, Lucide Icons, Vanilla CSS (Design Responsivo, Dark/Light Mode).
- Backend: Node.js, Express API, TypeScript, PostgreSQL Client (pg), JWT, BcryptJS.
- Banco de Dados: PostgreSQL 15-alpine com suporte a campos JSONB e Geocodificação.
- Implantação: Docker, Docker Compose, Portainer.io.

Portas do Ambiente Docker (docker-compose.yml):
- Frontend Web: Porta 8280 (mapeada para a porta interna 4000 do container regz-app).
- PostgreSQL: Porta 5434 (mapeada para a porta interna 5432 do container regz-postgres).


2. ESTRUTURA DO BANCO DE DADOS (POSTGRESQL 15)
-------------------------------------------------------------------------------

TABELA 1: perfis_acesso
Descrição: Armazena os perfis de acesso do sistema (RBAC - Role Based Access Control).
Campos:
  - id SERIAL PRIMARY KEY
  - nome VARCHAR(255) NOT NULL UNIQUE
  - descricao TEXT
  - is_admin BOOLEAN DEFAULT false
  - permissoes JSONB NOT NULL DEFAULT '{}'::jsonb
  - criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Perfis Padrão do Sistema:
  1. Administrador (is_admin = true, Acesso total a todas as abas e configurações)
  2. Gestor de RH (Acesso a colaboradores e campos personalizáveis)
  3. Operador (Leitura e escrita em colaboradores, sem acesso a campos e administração)
  4. Consulta (Somente leitura de dados e relatórios)

Estrutura da Coluna permissoes (JSONB):
{
  "home": "escrita" | "leitura" | "sem_acesso",
  "colaboradores": "escrita" | "leitura" | "sem_acesso",
  "campos": "escrita" | "leitura" | "sem_acesso",
  "administracao": "escrita" | "leitura" | "sem_acesso"
}


TABELA 2: usuarios
Descrição: Armazena os usuários autenticáveis que acessam a plataforma Regz.
Campos:
  - id SERIAL PRIMARY KEY
  - nome VARCHAR(255) NOT NULL
  - email VARCHAR(255) NOT NULL UNIQUE
  - senha_hash VARCHAR(255) NOT NULL
  - perfil_id INT REFERENCES perfis_acesso(id) ON DELETE SET NULL
  - ativo BOOLEAN DEFAULT true
  - criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Usuário Padrão Inicial:
  - E-mail: admin@regz.app
  - Senha: admin123 (Criptografada com bcrypt cost factor 10)


TABELA 3: cargos
Descrição: Armazena o catálogo de cargos e ocupações CBO oficiais (Classificação Brasileira de Ocupações - MTE/Brasil) com sinônimos e aliases de mercado.
Campos:
  - id SERIAL PRIMARY KEY
  - nome VARCHAR(255) NOT NULL UNIQUE
  - codigo_cbo VARCHAR(20)
  - sinonimos TEXT
  - criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP


TABELA 4: colaboradores
Descrição: Armazena os cadastros principais de colaboradores da organização.
Campos:
  - id SERIAL PRIMARY KEY
  - nome VARCHAR(255) NOT NULL
  - cpf VARCHAR(14) NOT NULL UNIQUE (Formato: 000.000.000-00)
  - cargo VARCHAR(255)
  - cep VARCHAR(9) (Formato: 00000-000)
  - logradouro VARCHAR(255)
  - numero VARCHAR(50)
  - complemento VARCHAR(255)
  - bairro VARCHAR(255)
  - cidade VARCHAR(255)
  - estado VARCHAR(2) (UF com 2 letras, ex: SP, RS, RJ)
  - latitude NUMERIC(10,8)
  - longitude NUMERIC(11,8)
  - foto_url TEXT (Armazena imagem comprimida ultraleve ~25KB em Base64 Data URL)
  - ativo BOOLEAN DEFAULT true
  - criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP


TABELA 5: campos_customizados
Descrição: Permite a definição de novos campos dinâmicos sem alterar o schema do banco de dados, com suporte a Soft Delete (Inativação e Reativação).
Campos:
  - id SERIAL PRIMARY KEY
  - nome VARCHAR(255) NOT NULL UNIQUE
  - tipo VARCHAR(50) DEFAULT 'texto' (Valores aceitos: texto, numero, data, selecao, booleano, email, cpf, telefone)
  - opcoes TEXT (Lista de opções separadas por vírgula para o tipo selecao)
  - obrigatorio BOOLEAN DEFAULT false
  - min_caracteres INT
  - max_caracteres INT
  - ativo BOOLEAN DEFAULT true (Soft Delete: campos inativos são ocultados em novos cadastros preservando dados históricos)
  - empresa_id INT REFERENCES empresas(id) ON DELETE CASCADE
  - criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Campos Customizados Padrão:
  - Setor / Departamento (tipo: selecao)
  - Nome da Mãe (tipo: texto)
  - Nome do Pai (tipo: texto)
  - Estado Civil (tipo: selecao)
  - PIS / PASEP (tipo: texto)


TABELA 6: colaboradores_valores_customizados
Descrição: Armazena os valores preenchidos para os campos customizados de cada colaborador.
Campos:
  - id SERIAL PRIMARY KEY
  - colaborador_id INT REFERENCES colaboradores(id) ON DELETE CASCADE
  - campo_id INT REFERENCES campos_customizados(id) ON DELETE CASCADE
  - valor TEXT
  - CONSTRAINT unique_colab_campo UNIQUE (colaborador_id, campo_id)


3. REGRAS DE NEGÓCIO E COMPORTAMENTOS DO SISTEMA
-------------------------------------------------------------------------------

A. Autenticação e Autorização (RBAC):
- O login gera um token JWT enviado nas requisições no cabeçalho Authorization: Bearer <token>.
- O usuário Administrador possui acesso irrestrito a todas as funcionalidades. Na página Administração, todas as cores das badges de perfis (Admin com brilho, Gestor de RH, Operador, Consulta sem brilho), botões de ação e filtros são gerenciadas centralizadamente por Variáveis CSS Semânticas (--badge-admin-bg, --badge-rh-bg, --badge-operador-bg, --badge-consulta-bg, etc.) declaradas no topo do index.css para cada tema visual (Modo Padrão, Modo Claro e Modo Escuro).
- O sistema valida a permissão de escrita/leitura do usuário para exibir ou ocultar botões de ação (Criar, Editar, Remover).

B. Cadastro e Otimização de Fotos de Colaboradores:
- Ao enviar ou alterar a foto de um colaborador, a imagem é comprimida e convertida no navegador para Base64 ultraleve (~25KB) para otimizar o banco de dados.
- O botão "Remover Foto Atual" exibe uma estilização vermelha intensa (#f43f5e) sem brilho/sombra (box-shadow: none) e texto/ícone em branco (#ffffff) em todos os temas.

C. Validação de Dados, Máscaras & Crachá Digital:
- CPF: Validação de formato (000.000.000-00) e verificação de duplicidade no banco.
- CEP: Integração automática com a API ViaCEP para preenchimento automático de Logradouro, Bairro, Cidade e Estado.
- Crachá Digital & QR Code: Geração de QR Code 2D vetorizado (qrcode.react) e crachá corporativo com avatar, nome, CPF, cargo, registro e status do colaborador. O modal abre como um Pop-Up centralizado em primeiro plano (position: fixed, z-index: 999999) com fundo desfocado (.modal-backdrop), suporte a fechamento via tecla Esc e botões de ação ("Baixar QR Code (PNG)" e "Imprimir Crachá") padronizados na classe primária (btn-primary) em todos os temas.
- Botão "X" de Fechar Modals: Padronizado em todos os modals (.btn-close) como um botão circular vermelho translúcido (#fb7185) com aura/brilho neon, transição de escala e rotação de 90° no hover.

D. Busca, Filtro & Tabela de Colaboradores:
- Suporta busca unificada por Nome, CPF, Cargo, Cidade ou Nome Completo do Estado.
- Ao pesquisar pelo nome do Estado (ex: "São Paulo", "Rio Grande do Sul") ou sigla (ex: "SP", "RS"), o filtro normaliza acentos e localiza os colaboradores correspondentes.
- Suporta filtro por sub-abas de Colaboradores "Ativos" ou "Inativos".
- Painel da Coluna Ações: Configurado com largura expandida (165px) sem alça de redimensionamento (.resizer) na borda direita do cabeçalho, garantindo que os botões (QR Code, Google Maps e Inativar/Reativar) sejam exibidos por completo sem cortes.
- Controle de Perfis de Acesso & Matriz de Permissões (RBAC): A tabela de Perfis de Acesso não exibe matriz de checkboxes inline nas células, apresentando uma visualização limpa com Perfil, Descrição, Módulos Liberados e Ações (botão de lápis para edição e lixeira para exclusão). O modal "EDITAR PERFIL (RBAC)" e "CRIAR NOVO PERFIL DE ACESSO" contém uma tabela estruturada da Matriz de Permissões com colunas Módulo e Recurso, LEITURA e ESCRITA. Todo módulo ativado na navegação principal (Home, Colaboradores, Campos, Administração, Relatórios, Configurações, Departamentos) é sincronizado dinamicamente nos formulários de criação e edição. O fundo dos modais no modo tema padrão é 100% sólido e opaco (#0f172a) sem transparências, a opção de desativar perfil é desabilitada e travada como ativa para perfis de Administrador, e o fechamento do modal é estrito (não fecha ao clicar fora no backdrop, apenas via botão "X", botão "CANCELAR" ou tecla ESC).
- Expiração de Senhas (30 Dias) & Gestão de Chaves de Licença: Cada usuário possui um controle automático de validade de senha calculada em 30 dias a partir da coluna senha_atualizada_em. Apenas a conta Super Admin (Administrador Regz, admin@regz.app) é isenta de licença (exibindo '-' na coluna Licença) e possui a linha protegida contra edições ou exclusões (coluna Ações = '-'). Outros administradores e usuários comuns exigem licença ativa (Enterprise ou Trial) para evitar bloqueio em MODO SOMENTE LEITURA. Na aba Usuários do Sistema, a coluna "Licença" exibe a TAG do plano (Enterprise ou Trial, e '-' para Super Admin), a coluna "Exp." exibe tags compactas sem texto (ex: 🟢 (30d), 🟡 (5d), 🔴 (-2d)), e a tabela utiliza minWidth dinâmico (totalUserTableWidth) com a coluna Ações protegida com 165px mínimos. Ao clicar no botão de renovar licença, abre-se o Modal de Renovação/Alteração de Licença com suporte 100% responsivo a todos os 3 temas (Padrão, Claro e Escuro): no modo Claro, exibe fundo branco #ffffff com cartões #f8fafc/#f1f5f9 e textos escuros #0f172a/#64748b legíveis; no modo Escuro, usa #1b1b1f e #242429, com o botão CANCELAR estilizado com fundo escuro #141416; para licenças Trial, permite renovar por +30 dias ou converter para Enterprise (+120d ou +365d); para licenças Enterprise, permite converter para Trial (30 dias) ou adicionar +120d ou +365d. As chaves de licença são vinculadas estritamente no banco PostgreSQL via coluna usuarios.chave_licenca sincronizada bidirecionalmente com chaves_licenca.usuario_id através da rotina syncDatabaseLicenses, e os dias faltantes são calculados por subtração direta de datas de calendário ((data_expiracao::date - CURRENT_DATE)::int). Ao expirar o prazo (data_expiracao < CURRENT_TIMESTAMP), a chave é automaticamente invalidada no banco mudando o status para 'Expirada', exigindo uma nova chave válida para liberação. A sub-aba "Chaves de Licença" (exibida exclusivamente pelo Super Admin) possui alças arrastáveis (.resizer) em todas as colunas, persistência no localStorage (regz_licenca_column_widths), minWidth acumulado (totalLicTableWidth) impedindo compressão de campos e barra de rolagem horizontal automática.
- 149: - Expiração de Licenças & Coluna Validade: A coluna na tabela de usuários da Administração denomina-se **Validade** e exibe a contagem regressiva exata calculada a partir da data de expiração da chave de licença (`dias_restantes_licenca`), utilizando tags visuais compactas (ex: 🟢 (29d), 🟡 (5d), 🔴 (-2d)). As chaves de licença são vinculadas no banco PostgreSQL via `usuarios.chave_licenca` e `chaves_licenca.usuario_id` através da rotina `syncDatabaseLicenses`. Ao expirar a licença, a chave é automaticamente invalidada mudando o status para 'Expirada', exigindo uma nova chave emitida pelo Super Admin Regz.
- 150: - Arquitetura On-Premise & Portal Isolado Super Admin Regz (Grid de Cards Modernos, Vínculo Estrito de empresa_id, Rota /administracao & Sub-modais z-index 2000): O perfil Super Admin Regz (`admin@regz.app` ou `is_super_admin: true`) é o Licenciador Master da plataforma e possui o Portal Isolado Independente (`SuperAdmin.tsx`), acessível estritamente através da rota `/administracao` no navegador. Toda nova chave Master emitida através de `POST /api/licencas` grava obrigatoriamente a coluna `empresa_id` na tabela `chaves_licenca`, e o endpoint `GET /api/empresas/:id/licencas` executa rotinas de auto-recuperação/resgate de chaves de teste orfãs. A gestão de empresas clientes é realizada por um Grid de Cards Executivos (`.empresa-card`). Todos os sub-modais de ação (**Emitir Nova Chave Master**, **Renovar/Alterar Validade**, **Editar Empresa** e **Confirmar Exclusão**) utilizam sobreposição visual estrita (`z-index: 2000`). O Gerenciador de Licenças Master da Empresa conta com o botão de atalho **⚡ Emissão Rápida (1 Ano)** para gerar instantaneamente uma chave Enterprise de 365 dias. O modal de empresa inclui testador e provisionador inteligente de banco de dados (`POST /api/empresas/test-db`). Ao clicar no botão de exclusão de empresa cliente, o modal `ModalConfirmDeleteEmpresa` bloqueia a confirmação até que a palavra **"SIM"** seja digitada.
- 151: - Limpeza do Banco de Dados & Varredura Geral de Código: Foi executada varredura completa no projeto e no esquema do PostgreSQL. A tabela órfã de testes `teste` foi removida do banco via `DROP TABLE IF EXISTS teste;` no `initDb`. Todos os modais possuem escuta nativa para a tecla `ESC` (como no Crachá/QR Code de Colaboradores), e o testador de banco possui fechamento garantido de pools de conexão.
- 152: - Proteção contra Força Bruta no Login (Rate Limiting por IP/E-mail & Bloqueio Temporário): O endpoint `POST /api/auth/login` em `backend/src/index.ts` conta com sistema ativo de defesa contra ataques de força bruta. Tentativas de login mal-sucedidas são registradas no mapa `loginAttemptsMap` combinando a chave IP do cliente e e-mail. Ao acumular 5 falhas consecutivas, o acesso daquela chave é travado por 15 minutos (900s), retornando HTTP 429 com aviso do tempo restante para desbloqueio. Um login realizado com sucesso zera imediatamente o contador de falhas.
- 153: - Cadastro de Usuários Exclusivo no Card da Empresa (Super Admin) & Gestão RBAC no Admin Comum: A criação de contas de usuários de uma empresa cliente e o vínculo de chaves de licença master avulsas é atribuído **exclusivamente ao Super Admin Regz** no modal `👥 Usuários` do card da empresa (`SuperAdmin.tsx`). O botão `+ Novo Usuário` foi totalmente removido do painel do Admin comum (`Administracao.tsx`). No modal do Super Admin, a caixa de seleção exibe todas as chaves master ativas emitidas previamente para aquela empresa (`usuario_id IS NULL`), permitindo ao Super Admin cadastrar o usuário com Nome, E-mail, Senha, Perfil de Acesso (RBAC) e atrelar a chave master na criação. A tabela de licenças conta também com a ação `Desvincular Licença` (`POST /api/licencas/:id/desvincular`) para retornar uma chave atrelada ao status "Empresa / Avulso". O Admin comum possui foco total na aba `Perfis de Acesso & Permissões` (RBAC), onde gerencia, cria, edita e exclui perfis e permissões da sua empresa.

D. Estrutura do Banco de Dados PostgreSQL (Tabela `empresas`):
- Tabela `empresas`: `id` (SERIAL PRIMARY KEY), `razao_social` (VARCHAR), `nome_fantasia` (VARCHAR), `cnpj` (VARCHAR UNIQUE), `cep`, `logradouro`, `numero`, `complemento`, `bairro`, `cidade`, `estado`, `logo_url` (TEXT), `cor_primaria` (DEFAULT '#6366f1'), `cor_secundaria` (DEFAULT '#38bdf8'), `cor_destaque` (DEFAULT '#34d399'), `status` (DEFAULT 'Ativa'), `db_host` (VARCHAR), `db_port` (INT DEFAULT 5432), `db_user` (VARCHAR), `db_pass` (VARCHAR), `db_name` (VARCHAR), `criado_em` (TIMESTAMP). Chave estrangeira `empresa_id` em `usuarios` e `chaves_licenca`.

E. Seleção, Sinônimos e Validação Estrita no Campo Cargo / Função (CBO):
- Permite pesquisar os cargos oficiais da CBO por nome, pelo código numérico CBO ou por sinônimos/aliases comuns de mercado (ex: "Dev React", "Front-end", "Tech Lead", "DBA", "Carreteiro", "Empilhadeirista", "Copywriter", "Business Partner").
- O campo utiliza a técnica de controle de foco via useRef e handleClickOutside, permitindo clicar e arrastar o cursor para selecionar o texto normalmente.
- REGRA 158: Validação Estrita de Cargo/Função e Mapeamento de Sinônimos contra o Catálogo Oficial CBO (MTE/Brasil / eSocial):
  - É proibido cadastrar ou atualizar colaboradores com cargos arbitrários ou que não existam na base oficial da CBO.
  - Tabela `cargos` contém a coluna `sinonimos TEXT`, armazenando aliases usuais de mercado para cada ocupação CBO oficial.
  - No Frontend (`Colaboradores.tsx`), ao pesquisar por qualquer sinônimo (ex: "React" ou "Front-end"), o dropdown localiza instantaneamente o CBO correspondente ("Programador de internet - CBO 3171-20") e exibe a tag destacada com o sinônimo encontrado.
  - Ao submeter o formulário (`handleSubmit`), se um sinônimo for informado ou selecionado, o sistema converte e grava o nome canônico oficial da CBO. Se o cargo for inexistente, exibe alerta visual imediato ("⚠️ Cargo não consta na lista CBO") e bloqueia a submissão com a mensagem `"O cargo/função informado não consta na lista oficial da CBO. Selecione uma ocupação válida da lista de sugestões."`.
  - No Backend (`backend/src/index.ts`), os endpoints `POST /api/colaboradores` e `PUT /api/colaboradores/:id` validam o campo `cargo` contra `nome`, `codigo_cbo` e `sinonimos` na tabela `cargos`. Caso seja um sinônimo, resolve automaticamente para o nome canônico oficial CBO. Se for inválido, a requisição é rejeitada com erro HTTP 400.

Modo Escuro [data-theme="dark"] (Fundo preto/cinza #121214 / #141416, cartões em #121214, botões inativos de Administração em #1b1b1f, botões de ação de auditoria 'Exportar CSV' e 'Atualizar Logs' com fundo #141416, botões da página Campos com brilho branco discreto box-shadow: 0 2px 8px rgba(255, 255, 255, 0.12), avatar do usuário sem brilho com box-shadow: none, badges de CBO em #141416 com texto branco e borda suave).

  - Campos inativados são omitidos automaticamente no cadastro de novos colaboradores, mas todos os dados preenchidos em colaboradores existentes são integralmente preservados no banco PostgreSQL (`colaboradores_valores_customizados`) e permanecem disponíveis em consultas, relatórios e exportações.
